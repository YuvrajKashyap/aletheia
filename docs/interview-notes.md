# Interview Notes

This document helps explain Aletheia clearly in interviews. It is not a resume bullet list.

## 30-Second Explanation

Aletheia is a production-style retrieval and evaluation platform. It supports BM25, dense retrieval, hybrid reciprocal rank fusion, and cross-encoder reranking over SciFact. It stores traces, runs qrels-backed evaluations, compares experiment configs, replays saved queries, tracks index versions, and exposes operational health through a Next.js dashboard backed by FastAPI.

## 2-Minute Technical Explanation

The system has a FastAPI backend with PostgreSQL metadata, Redis/RQ workers, OpenSearch for BM25, Qdrant for vectors, local sentence-transformer embeddings, and a cross-encoder reranker. SciFact documents, benchmark queries, and qrels are ingested into Postgres. Documents are chunked, indexed into OpenSearch and Qdrant, and retrieved through four modes: BM25, dense, hybrid RRF, and hybrid rerank.

Every search can produce a query trace with stage-level candidates, scores, ranks, and latency. Evaluation uses real SciFact qrels, maps chunk hits back to document IDs, deduplicates documents, and computes Recall@5, Recall@10, MRR@10, NDCG@10, and latency metrics. The frontend exposes search, traces, evaluation runs, experiment comparisons, index state, dataset inspection, replay, and system health.

The public demo is hosted on Vercel in snapshot mode. It uses real exported local outputs instead of pretending to run expensive live search infrastructure publicly.

## System Architecture Explanation

FastAPI owns all backend logic. The frontend never talks directly to PostgreSQL, OpenSearch, Qdrant, or Redis. Background work runs through Redis/RQ. Indexes are versioned, and active index changes are explicit. Evaluation and replay write structured reports and database records for inspection.

## Retrieval Explanation

BM25 handles lexical matching through OpenSearch. Dense retrieval uses `BAAI/bge-small-en-v1.5` embeddings and Qdrant. Hybrid retrieval uses RRF because BM25 and dense scores are not directly comparable. Hybrid rerank reranks a bounded top-N candidate set with `cross-encoder/ms-marco-MiniLM-L-6-v2` to expose the latency and quality tradeoff.

## Evaluation Explanation

SciFact qrels are document-level. Aletheia retrieves chunks, maps each chunk to its parent document, deduplicates document IDs, then computes metrics. This prevents multiple chunks from the same document from inflating scores.

## Production Concerns Explanation

The project includes versioned indexes, async jobs, health checks, worker heartbeat, system events, CI, local smoke checks, Dockerfiles, deployment docs, and snapshot demo mode. Public admin actions are disabled in snapshot mode.

## Public Demo Explanation

The public demo uses real precomputed outputs generated by the full local pipeline. Live retrieval, reranking jobs, index rebuilds, and admin actions are disabled publicly to avoid always-on search and ML infrastructure costs. The full live stack is still documented and runnable locally.

## Why Redis/RQ Matters

Evaluation, indexing, comparisons, and replay can be expensive. Redis/RQ separates these jobs from normal API requests and gives the platform job IDs, status, and worker boundaries.

## Why Query Tracing Matters

Retrieval systems fail in subtle ways. Query traces show which candidates came from BM25, dense retrieval, fusion, and reranking. This makes ranking behavior debuggable instead of opaque.

## Why Evaluation Correctness Matters

Without qrels alignment and document-level deduplication, metrics can look better than they are. Aletheia preserves correctness by scoring document IDs against real relevance judgments.

## Likely Q&A

### Why not a chatbot?

The project is about retrieval infrastructure, ranking, evaluation, and observability. It retrieves and explains search behavior instead of generating answers.

### Why RRF?

BM25 scores and dense vector scores have different meanings and scales. RRF combines ranked lists without pretending raw scores are comparable.

### Why reranker top-N?

Cross-encoder reranking is expensive. Reranking a bounded candidate set gives better ranking signal while keeping latency controlled.

### Why Qdrant and OpenSearch?

OpenSearch is a real BM25 lexical search engine. Qdrant is a real vector search engine. Keeping them separate makes retrieval stages and hybrid behavior easier to inspect.

### Why RQ not Celery?

RQ is simpler and adequate for this project. It demonstrates async job boundaries without adding Celery's operational complexity.

### Why snapshot public demo?

The full search stack depends on OpenSearch, Qdrant, Redis, workers, and local ML models. Snapshot mode hosts real exported outputs at low cost without faking live infrastructure.

### How does Atlas integrate?

Atlas can crawl, clean, and store web documents. Aletheia can index that corpus, run BM25/dense/hybrid/rerank retrieval, trace queries, and evaluate or replay search behavior over Atlas data.
